# CatalogGuard

> Status: **IN DEVELOPMENT — functional MVP available**

CatalogGuard is a configurable metadata quality and reconciliation engine that detects, classifies, and helps resolve inconsistencies between internal and external catalogs. Music publishing metadata is the primary case study.

## Why this project exists

Catalog reconciliation is not just a CSV comparison problem. Reliable workflows need source preservation, normalization, entity matching, validation rules, exception management, auditability, and human review when evidence is ambiguous. CatalogGuard demonstrates that workflow end to end without claiming production publishing experience.

## Data model

Each source is represented by four related tables:

- `works`: composition-level metadata and ISWC
- `parties`: composers/publishers and IPI
- `ownership`: work-to-party relationships and ownership shares
- `recordings`: recording-level metadata and ISRC

Keeping works and recordings separate is intentional: an ISWC identifies a musical work/composition, while an ISRC identifies a recording.

## Matching strategy

CatalogGuard is conservative by design.

1. Exact ISWC evidence is prioritized.
2. If ISWC matches but composer IPI conflicts, the pair is sent to `MANUAL_REVIEW`.
3. When identifiers are absent, normalized title/composer/publisher similarity is used only to create review candidates.
4. Ambiguous records are not silently corrected.

A perfect text similarity score is therefore not automatically equivalent to perfect entity-match confidence.

| DQ002 | Missing IPI |

| DQ007 | Possible fuzzy duplicate |
| DQ008 | Work missing from external catalog |

| DQ010 | Composer-name inconsistency |

## Synthetic case study

The repository includes synthetic music metadata with deliberately introduced quality problems such as missing identifiers, duplicate ISWCs, ownership totals that do not equal 100%, textual variations, identifier conflicts, publisher discrepancies, and source-only works. No final metric is hard-coded: quality metrics are generated by the pipeline.

## Run locally

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
python main.py
```

Generated outputs include:

- `catalogguard.db`
- `reports/quality_summary.csv`
- `reports/matches.csv`
- `reports/exceptions.csv`
- `reports/reconciliation.csv`
- `reports/catalogguard_report.xlsx`

Run tests:

```bash
pytest
```

Open the dashboard:

```bash
streamlit run app/dashboard.py
```

## Current limitations

- Synthetic portfolio data, not production catalog data.
- Matching heuristics are intentionally interpretable rather than ML-based.
- CWR/ACK processing is not implemented in the MVP.
- Curve integration is not implemented.
- Manual review status is generated as data but is not yet persisted through an interactive write-back workflow.
- Threshold calibration will require a labeled benchmark dataset in a later phase.

## Planned next steps

- Persist manual-review decisions and audit history.
- Add configurable matching weights and thresholds.
- Add ISRC-level reconciliation rules.
- Add richer SQL analytics.
- Add Google Sheets / Apps Script integration as a learning extension.
- Build a labeled evaluation set for precision/recall measurement.

## Portfolio integrity

It does **not** represent prior professional experience with Curve, CWR production workflows, ACK processing, or music publishing operations.
